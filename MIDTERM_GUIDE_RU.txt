2. Как всё связано

Браузер или curl → localhost:8081 → контейнер app:8080 → сервис db:5432 → PostgreSQL → именованный volume на диске Docker.

Контроллер принимает HTTP-запрос. Service выполняет логику. Repository обращается к базе через Spring Data JPA. Entity Student описывает запись. Dockerfile упаковывает приложение. Compose запускает приложение и базу вместе. Jenkins получает код из GitHub, собирает его, тестирует и проверяет Docker-образ.

После git push Jenkins периодически проверяет изменения (pollSCM), поэтому CI не зависит от открытого входящего порта на твоём ноутбуке. Сам Jenkins не выкладывает приложение автоматически: в задании достаточно Checkout → Build → Test → Docker Build → Verify. Локальный запуск Compose выполняется отдельно.

5. Linux — что писать и что объяснять

Перейди в корень проекта. Команда pwd подтверждает, где ты находишься:

   cd /home/eduard/devops/kim-eduard-student-api
   pwd
   mkdir -p scripts logs backups src
   touch logs/Kim_Eduard_system_report.log
   find . -maxdepth 2 -not -path './.git*' -not -path './.gradle*' -not -path './build*' -print

mkdir создаёт папки; -p также создаёт недостающих родителей и допускает уже существующие папки. touch создаёт пустой файл, если его ещё нет; существующий файл он НЕ обнуляет. Если преподаватель просит именно создать новый пустой лог, делай это в новой учебной копии, а не затирай сохранённое доказательство.

Показать исходник:

   cat scripts/Kim_Eduard_system_report.sh

Если попросят написать скрипт вручную, минимальный рабочий вариант для запуска из корня проекта:

   cat > scripts/Kim_Eduard_system_report.sh <<'EOF'
   #!/usr/bin/env bash
   set -euo pipefail
   mkdir -p logs
   {
       echo 'Student: Kim Eduard | IT2-2313 | ID 37324'
       date
       whoami
       cat /etc/os-release
       uname -r
       lscpu
       free -h
       df -h
       df -h .
   } | tee logs/Kim_Eduard_system_report.log
   EOF

В готовом репозитории версия чуть удобнее: она вычисляет путь к корню проекта, поэтому работает и из другого каталога. Не перезаписывай готовый файл без задания преподавателя; тренироваться можно в отдельной копии.

Что означает каждая строка:
  #!/usr/bin/env bash — выбрать Bash как интерпретатор;
  set -e — завершить скрипт при необработанной ошибке команды;
  -u — ошибка при обращении к неопределённой переменной;
  pipefail — ошибка команды в конвейере делает весь конвейер неуспешным;
  { ...; } — объединить вывод нескольких команд;
  echo — вывести текст;
  date — дата и время;
  whoami — имя текущего пользователя;
  /etc/os-release — сведения о Linux-дистрибутиве;
  uname -r — версия ядра;
  lscpu — CPU;
  free -h — оперативная память и swap в удобных единицах;
  df -h — занятое и свободное место в файловых системах;
  df -h . — файловая система текущего каталога;
  | — передать вывод следующей команде;
  tee — одновременно вывести на экран и записать в файл.

Права и запуск:

   chmod 744 scripts/Kim_Eduard_system_report.sh
   ls -l scripts/Kim_Eduard_system_report.sh
   ./scripts/Kim_Eduard_system_report.sh

Ожидаемые права: -rwxr--r--. Именно 744 требуется в задании: владелец читает, пишет и запускает (4+2+1=7), группа только читает (4), остальные только читают (4). Частый ответ 755 здесь не подходит: он разрешает группе и остальным ещё и запуск.

Git сохраняет признак executable, но не точный режим 744. После клонирования chmod 744 надо повторить; prepare_local.sh делает это автоматически.

Бэкап и анализ:

   cp README.md backups/Kim_Eduard_README_backup.md
   ls -l backups/Kim_Eduard_README_backup.md
   cmp README.md backups/Kim_Eduard_README_backup.md && echo 'Backup matches README'
   ps aux
   pgrep -af java
   tail -n 5 logs/Kim_Eduard_system_report.log
   grep -n 'Kim' logs/Kim_Eduard_system_report.log
   grep -n 'Kim' logs/Kim_Eduard_system_report.log > Kim_Eduard_log_analysis.txt
   cat Kim_Eduard_log_analysis.txt

cp копирует. cmp без вывода и с кодом 0 означает одинаковые файлы; && запускает следующую команду только при успехе предыдущей. ps aux показывает процессы всех пользователей. pgrep -af java ищет Java-процессы и показывает PID с командой. tail -n 5 берёт последние пять строк. grep ищет совпадение, -n добавляет номер строки.

«> создаёт файл или перезаписывает его содержимое. >> добавляет в конец. Например echo hello > demo.log заменяет содержимое; echo again >> demo.log дописывает строку».

6. Git — показать уже выполненный индивидуальный workflow

   git status
   git remote -v
   git branch -a
   git tag -n
   git log --graph --oneline --decorate --all

В истории есть начальный коммит с твоим именем, два содержательных коммита CRUD-ветки, её merge, изменения одной строки README на двух ветках, реальное разрешение конфликта и тег v1.0-kim-eduard. Ветка CRUD добавляет поиск по имени без учёта регистра и тесты. Ветка documentation участвует в конфликте. Ветка ci-demo хранит учебную ошибку и её исправление.

Команды с нуля — это справочник для НОВОЙ учебной папки. Не надо заново git init или создавать существующие ветки в рабочем репозитории:

   git init -b main
   git config user.name 'Kim Eduard'
   git config user.email '230118810+EdKimDA@users.noreply.github.com'
   git add .
   git commit -m 'Initial commit: Kim Eduard Student API'
   git switch -c feature/kim-eduard-crud
   # Изменить код одной CRUD-операции.
   git add src
   git commit -m 'Kim Eduard: add case-insensitive student search'
   # Добавить тесты и объяснение в README.
   git add README.md src/test
   git commit -m 'Kim Eduard: test and document filtered CRUD reads'
   git switch main
   git merge --no-ff feature/kim-eduard-crud

git add переносит текущую версию файла в staging area — список содержимого будущего коммита. commit создаёт локальную точку истории. push отправляет коммиты на удалённый сервер. Коммит сам по себе ничего не публикует в GitHub.

Чтобы показать конфликт вручную, используй НОВЫЕ имена веток в учебной копии. Сначала убедись в чистом git status:

   git switch main
   git switch -c feature/kim-eduard-documentation-practice
   # В редакторе изменить строку Documentation status в README.
   git add README.md
   git commit -m 'Kim Eduard: practice documentation update'
   git switch main
   # Эту же строку изменить ДРУГИМ текстом.
   git add README.md
   git commit -m 'Kim Eduard: practice main documentation update'
   git merge feature/kim-eduard-documentation-practice
   git status

При конфликте Git пишет CONFLICT и вставляет <<<<<<<, =======, >>>>>>>. Открой README, выбери или объедини нужный текст, удали все маркеры. Затем:

   git add README.md
   git commit -m 'Kim Eduard: resolve the README conflict'
   git log --graph --oneline --decorate --all

Не оставляй маркеры в файле и не используй git reset --hard для «лечения» неизвестных изменений. Если нужно отменить именно незавершённый merge, сначала оцени свои правки и используй git merge --abort.

Публикация и тег (remote и обязательный тег уже созданы):

   git remote -v
   git push origin main
   git push origin feature/kim-eduard-crud feature/kim-eduard-documentation feature/kim-eduard-ci-demo
   git tag -n
   git show v1.0-kim-eduard --stat

В новом репозитории команды были бы git remote add origin URL, git push -u origin main, git tag -a v1.0-kim-eduard -m 'Kim Eduard release 1.0', git push origin v1.0-kim-eduard. Не переназначай уже опубликованный тег, чтобы он «переехал» на последний коммит. Тег — фиксированная отметка выбранного релиза, main продолжает развиваться.

.gitignore исключает .env, build, .gradle, локальные логи и evidence. .env.example содержит структуру настроек с заглушкой пароля и может быть публичным. Если секрет уже попал в коммит, добавление в .gitignore не удаляет его из старой истории: секрет нужно заменить, затем отдельно чистить историю при необходимости.

7. Java и Gradle — что ты должен понимать

Основные файлы находятся в src/main/java/edu/kim/studentapi/.
  StudentApiApplication — точка входа Spring Boot.
  Student — JPA Entity, поля студента и ID, который генерирует БД.
  StudentRequest — входной JSON, проверки обязательных полей и email.
  StudentController — HTTP-методы /api/students.
  StudentService — операции и правила обработки студента.
  StudentRepository — доступ к PostgreSQL через Spring Data JPA.
  ApiExceptionHandler — преобразует ошибки в понятные HTTP-ответы.
  ProjectController — показывает имя, группу, ID и версию на главной странице.
  application.yml — порт, настройки JPA и подключение через переменные окружения.
  src/test — автоматические проверки CRUD и ошибок.

build.gradle указывает Java 21, плагины и зависимости. Gradle скачивает библиотеки и вызывает компилятор. gradlew — скрипт запуска закреплённого Gradle, gradle-wrapper.properties задаёт версию дистрибутива. gradle.properties содержит appVersion.

   ./gradlew --no-daemon clean assemble
   ./gradlew --no-daemon test
   ls -lh build/libs/app.jar

clean удаляет прошлые результаты сборки; assemble собирает артефакты, но не запускает тесты. test запускает тесты. bootJar создаёт исполняемый Spring Boot JAR. build обычно включает и сборку, и проверки. --no-daemon не оставляет постоянный Gradle daemon; Gradle при необходимости может запустить одноразовый процесс.

В main 16 тестов. Они используют отдельную временную H2-базу в PostgreSQL compatibility mode, поэтому Jenkins не требует пароль рабочей PostgreSQL. Это не делает H2 полностью идентичной PostgreSQL: отдельно выполнены реальные HTTP-проверки и проверка PostgreSQL в Compose.

8. Dockerfile — показать и объяснить строки

   cat Dockerfile

FROM eclipse-temurin:21-jdk AS build
  Официальный образ с Java Development Kit: нужен компилятор для сборки. build — имя стадии.
WORKDIR /workspace
  Рабочая папка последующих инструкций внутри образа.
COPY gradlew settings.gradle build.gradle gradle.properties ./
COPY gradle/ ./gradle/
  Копирование wrapper и конфигурации Gradle из build context.
RUN chmod +x gradlew
  Выдать wrapper право запуска в образе.
COPY src/ ./src/
  Скопировать исходники.
RUN ./gradlew --no-daemon clean bootJar -x test
  Собрать JAR. Здесь тесты исключены, поскольку Jenkins запускает их отдельной предыдущей стадией. При ручной сборке сначала сам выполни ./gradlew test.
FROM eclipse-temurin:21-jre-jammy AS runtime
  Начало итоговой стадии с Java Runtime. Компилятор в готовом приложении не нужен.
WORKDIR /app
RUN groupadd --system app && useradd --system --gid app --home-dir /app app
  Создать непривилегированного пользователя.
COPY --from=build --chown=app:app /workspace/build/libs/app.jar ./app.jar
  Забрать только готовый JAR из первой стадии и назначить владельца.
USER app
  Дальнейший запуск приложения не от root.
EXPOSE 8080
  Обозначить порт приложения. Это не публикация порта на компьютере.
ENTRYPOINT ["java", "-XX:MaxRAMPercentage=65.0", "-jar", "/app/app.jar"]
  Команда при запуске контейнера. Настройка памяти ограничивает долю памяти для Java heap, а не всю память Java-процесса.

RUN выполняется во время docker build. ENTRYPOINT/CMD задают запуск контейнера. Multi-stage оставляет инструменты сборки вне итоговой стадии.

Ручная сборка и сведения об образе:

   ./gradlew --no-daemon test
   docker build -t kim-eduard-student-api:v1.0.1-kim-eduard-37324 .
   docker image ls kim-eduard-student-api
   docker image inspect kim-eduard-student-api:v1.0.1-kim-eduard-37324 --format 'ID={{.Id}} Created={{.Created}} Size={{.Size}}'

Точка в docker build — build context, каталог доступных для COPY файлов. -t задаёт имя:тег. .dockerignore исключает ненужные файлы и секреты из контекста. Size в inspect — байты, docker image ls показывает удобные единицы; на разных платформах цифры могут отличаться.

9. Compose — что показать и выполнить

   cat docker-compose.yml

name задаёт личное имя Compose-проекта. services описывает app и db. build: . собирает app из Dockerfile. image задаёт персональный тег. ports связывает 127.0.0.1:8081 компьютера с 8080 контейнера. environment передаёт настройки. ${...} подставляется Compose из окружения/.env. Запись с :? останавливает запуск, если пароль отсутствует.

DB_URL содержит jdbc:postgresql://db:5432/kim_eduard_students. db — имя сервиса и DNS-имя в общей Docker-сети. localhost внутри app означает сам app, поэтому база там недоступна. Сеть обеспечивает связь контейнеров; volume хранит файлы БД независимо от жизненного цикла контейнера.

healthcheck запускает pg_isready. depends_on с service_healthy ждёт готовности БД до старта приложения. Двойной $$ сохраняет переменную для раскрытия внутри контейнера, вместо ранней подстановки Compose. Проверка готовности не заменяет все будущие проверки подключения и повторные попытки приложения.

Не выводи docker compose config, .env или полный Config.Env при демонстрации: там может оказаться пароль. Для структуры достаточно исходного YAML с именами переменных.

Команды управления:

   docker compose up -d --build --wait
   docker compose ps
   docker compose logs --tail 40 app
   docker inspect kim-eduard-student-api-app --format 'Image={{.Config.Image}} User={{.Config.User}} Ports={{json .NetworkSettings.Ports}}'
   docker inspect kim-eduard-student-api-db --format '{{json .Mounts}}'
   docker network inspect kim-eduard-student-api-network --format '{{json .Containers}}'
   docker compose exec app java -version
   docker compose exec app id
   docker compose stop app
   docker compose ps -a
   docker compose start app
   curl -sS http://127.0.0.1:8081/actuator/health

-d — работать в фоне. logs читает stdout/stderr процесса. exec запускает дополнительную команду в уже работающем контейнере. stop останавливает контейнер, start запускает тот же контейнер. restart останавливает и запускает. Изменённый образ применяется через up -d --build, а не просто restart.

10. CRUD через curl — вводить в Ubuntu

Сначала создай демонстрационную запись с уникальным studentId. Уникальность нужна, чтобы повторный показ не получил 409. Основную запись 37324 можно оставить для проверки сохранности.

   API=http://127.0.0.1:8081
   DEMO_STUDENT_ID="37324-demo-$(date +%s)"
   curl -sS -i -X POST "$API/api/students" \
     -H 'Content-Type: application/json' \
     -d "{\"name\":\"Kim Eduard\",\"email\":\"kim.eduard@example.com\",\"groupName\":\"IT2-2313\",\"studentId\":\"$DEMO_STUDENT_ID\"}"

Ожидается HTTP 201 Created, заголовок Location и JSON с id. id — ключ записи в базе; studentId — учебный идентификатор из запроса. Это разные поля! Запиши полученный id в переменную; например, если ответ содержит id 7:

   ID=7

Число 7 — пример, замени на число из своего ответа. Не предполагается, что оно всегда 1 или 2.

   curl -sS -i "$API/api/students"
   curl -sS -i "$API/api/students/$ID"
   curl -sS -i -G "$API/api/students" --data-urlencode 'name=kim'
   curl -sS -i -X PUT "$API/api/students/$ID" \
     -H 'Content-Type: application/json' \
     -d "{\"name\":\"Kim Eduard Updated\",\"email\":\"kim.eduard@example.com\",\"groupName\":\"IT2-2313\",\"studentId\":\"$DEMO_STUDENT_ID\"}"
   curl -sS -i -X DELETE "$API/api/students/$ID"
   curl -sS -i "$API/api/students/$ID"

Ожидаемые статусы по порядку: GET list 200; GET id 200; поиск 200; PUT 200; DELETE 204 без тела; повторный GET удалённой записи 404. curl -i показывает заголовки и статус. -X выбирает HTTP-метод, -H задаёт заголовок, -d передаёт тело. PUT в этом проекте ожидает все поля, поэтому не отправляй только name.

Для дополнительной проверки 400 можно отправить пустое name или неправильный email. Для 409 — повторить POST с уже существующим studentId.

Автоматический помощник после ручного показа:

   python3 scripts/api_smoke_test.py

Он создаёт свою временную запись, проверяет ответы и удаляет только её, сохраняя результат в evidence/api-smoke.json. Это удобная самопроверка; на live coding всё равно нужно понимать curl и статусы.

11. Как доказать, что данные сохраняются

   curl -sS http://127.0.0.1:8081/api/students
   python3 scripts/check_persistence.py

Помощник находит или создаёт личную запись с studentId 37324, сохраняет её JSON, выполняет docker compose down, затем up -d --wait и читает запись по тому же id. Успех означает, что запись сохранилась в PostgreSQL. Результат — evidence/postgres-persistence.json. Личную запись он оставляет.

Для ручного объяснения: сохрани id нужной записи, выполни docker compose down, затем docker compose up -d --wait, дождись HTTP-готовности и повтори GET /api/students/ID. down удаляет контейнеры и сеть проекта, но именованный volume по умолчанию остаётся. Не добавляй -v: эта опция удаляет volume и данные. Если задача только «перезапустить сервисы», достаточно docker compose restart; down/up даёт ещё более явную проверку независимости данных от контейнера.

12. Изменение версии и пересборка

В ходе подготовки версия изменена с 1.0.0 на 1.0.1. Для новой демонстрации можно перейти с 1.0.1 на 1.0.2:

   # В редакторе gradle.properties: appVersion=1.0.2
   # В docker-compose.yml: image: kim-eduard-student-api:v1.0.2-kim-eduard-37324
   git diff
   docker compose up -d --build --wait
   curl -sS http://127.0.0.1:8081/
   docker compose ps
   curl -sS http://127.0.0.1:8081/api/students

Версия на главной странице должна стать 1.0.2, новая запись image должна появиться в docker image ls, прежний студент должен остаться. Менять только тег недостаточно: версия приложения берётся из Gradle build info и попадает в новый JAR при сборке. Обнови также примеры версии README, если оформляешь новый релиз.

13. Jenkins — что настроено и как показать

Открой Job Kim_Eduard_Student_API → Configure → Pipeline.
  Definition: Pipeline script from SCM.
  SCM: Git.
  Repository URL: https://github.com/EdKimDA/kim-eduard-student-api.git
  Branch Specifier для обычной работы: */main
  Script Path: Jenkinsfile

Публичный репозиторий для чтения не требует credentials. Для private GitHub использовались бы Jenkins Credentials с ограниченным токеном или SSH-ключом, указанным в SCM. Пароли нельзя писать в Jenkinsfile. В текущем учебном окружении Jenkins работает как eduard в Ubuntu, где доступны Git, JDK 21 и Docker Desktop. Отдельный агент не создан: сборка идёт на встроенном executor; для учебного локального задания он уже проверен, для реальной инфраструктуры обычно выделяют агентов.

Показать Jenkinsfile в редакторе:
  pipeline — Declarative Pipeline;
  agent any — выбрать доступный исполнитель;
  skipDefaultCheckout(true) — не выполнять неявный checkout перед нашей стадией;
  disableConcurrentBuilds — не запускать две сборки этой Job одновременно;
  timeout — ограничить время;
  pollSCM('H/2 * * * *') — примерно раз в две минуты проверить изменения выбранной ветки; H распределяет моменты проверок по хэшу Job;
  environment — личные имя, ID и имя образа;
  Checkout — очистить workspace и checkout scm из настроек Job;
  Build — ./gradlew --no-daemon clean assemble;
  Test — ./gradlew --no-daemon test;
  Docker Build — прочитать appVersion и собрать персональный образ;
  Verify — docker image inspect, затем сообщение VERIFIED;
  post always — сохранить JUnit-результаты и JAR даже после ошибки, если файлы появились.

Ненулевой код команды sh завершает стадию ошибкой. Здесь нет игнорирования test через || true или returnStatus без проверки. Поэтому после упавших тестов Docker Build и Verify пропускаются. junit публикует результат, но не подменяет фактический запуск тестов.

Важно: Verify проверяет существование образа, а не запускает приложение и не деплоит его. Не надо добавлять Docker Run или открывать Jenkins в интернет, чтобы «выполнить CI/CD»: автоматический deployment в DOCX не обязателен.

Для обычного запуска нажми «Собрать сейчас»/Build Now. Открой номер сборки → Console Output и Stages. Покажи имя Kim Eduard в логе, commit hash, результаты тестов, тег образа и Finished: SUCCESS. История с фактическими номерами и причинами сборок сохранена локально в evidence/verification-summary.txt после подготовки.

14. Намеренная ошибка и исправление

Ветка feature/kim-eduard-ci-demo содержит два коммита: первый добавил неправильную проверку имени, второй исправил её. В main эта ошибка не попадала. В неуспешной сборке ControlledFailureTests ожидал Incorrect Author вместо Kim Eduard. Build прошёл, Test упал: 17 tests completed, 1 failed. Следующие стадии были пропущены. После исправления прошли все 17 тестов ветки; в main остаются 16 основных тестов.

Для повторного live coding делай НОВУЮ test-ветку от main:

   git status
   git switch main
   git pull --ff-only
   git switch -c feature/kim-eduard-ci-practice

В редакторе добавь src/test/java/edu/kim/studentapi/ControlledFailureTests.java:

   package edu.kim.studentapi;
   import org.junit.jupiter.api.Test;
   import static org.assertj.core.api.Assertions.assertThat;
   class ControlledFailureTests {
       @Test void authorNameIsCorrect() {
           assertThat("Kim Eduard").isEqualTo("Incorrect Author");
       }
   }

   git add src/test/java/edu/kim/studentapi/ControlledFailureTests.java
   git commit -m 'Kim Eduard: demonstrate a controlled failing CI test'
   git push -u origin feature/kim-eduard-ci-practice

В Configure Job временно выбери */feature/kim-eduard-ci-practice, Save и Build Now. Дождись FAILURE. Покажи ошибку assertion в Console Output и пропущенные стадии. Затем исправь ожидание на isEqualTo("Kim Eduard"):

   git add src/test/java/edu/kim/studentapi/ControlledFailureTests.java
   git commit -m 'Kim Eduard: fix the controlled CI test'
   git push

После исправления нажми Build Now и покажи SUCCESS. Автоматический запуск отдельно докажи следующим коммитом в main после восстановления Job. После смены ветки Job сначала выполни успешную базовую сборку: это обновит сведения checkout для polling. Обычно проверка Git занимает до нескольких минут, плюс время сборки. Первый ручной запуск также нужен, чтобы Jenkins прочитал triggers из Jenkinsfile.

После демонстрации верни Job на */main и локально git switch main. Новую ветку с неправильным тестом в main не сливай. Ошибка и исправление демонстрируются отдельными коммитами и сборками; для автоматизации ниже используется следующий коммит main.

Чтобы доказать автоматизацию на main после возвращения Job и успешной базовой сборки main, сделай осмысленную маленькую правку README или изменение версии, commit и push. После этого не нажимай Build Now. Причина новой сборки должна быть Started by an SCM change. Покажи, что сборка стартовала без Build Now, открой её причину и hash. Один успешный ручной запуск ещё не доказывает автоматический trigger.

15. Типичные проблемы и порядок диагностики

API недоступен:
  docker compose ps -a
  docker compose logs --tail 80 app
  docker compose logs --tail 50 db
  curl -i http://127.0.0.1:8081/actuator/health
Проверь порт 8081 и рабочую папку. После старта JVM подожди готовности. В app указан порт 8080, снаружи обращайся к 8081. Connection refused — соединение не установлено; HTTP 404 — сервер ответил, но путь или запись не найдены.

Ошибка PostgreSQL:
  docker compose exec db sh -lc 'pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
  docker inspect kim-eduard-student-api-db --format '{{.State.Health.Status}}'
Проверь db:5432 в DB_URL, общую сеть, статус базы и соответствие пароля в .env существующей БД. POSTGRES_PASSWORD инициализирует новую БД; смена этой переменной не меняет пароль в уже заполненном volume. Не лечи всё удалением volume: сначала сохрани данные и выясни причину.

Gradle не запускается:
  chmod +x gradlew
  java -version
  javac -version
  ./gradlew --no-daemon test --stacktrace
Permission denied — права; /bin/sh^M или bad interpreter — CRLF, нужен LF; toolchain/compile error — JDK или код; Could not resolve dependency — сеть/координаты зависимости. Не скачивай другую случайную версию Gradle вместо wrapper.

Docker Build падает после успешного Test:
Открой именно стадию Docker Build и первую содержательную ошибку. Проверь docker version на агенте, доступ к daemon, официальный base image/сеть, наличие Dockerfile и COPY-путей. Повтори docker build --progress=plain -t kim-eduard-student-api:debug . из корня проекта на том же исполнителе. Успешный Java compile не проверяет Dockerfile.

Jenkins не видит изменение:
Проверь, что git push действительно прошёл, ветка Job совпадает с изменённой веткой, первый Jenkinsfile уже был выполнен, Poll SCM включён. Открой «Лог опроса Git». H/2 — проверка изменений, а не обязательная сборка каждые две минуты при отсутствии изменений. Не путай сохранение файла на диске с commit и push.

Jenkins не открывается:
Проверь процесс, адрес 127.0.0.1:8080 и терминал запуска. Не меняй сразу bind на 0.0.0.0: это расширяет доступ к Jenkins. На этом компьютере уже проверена работа через localhost.

GitHub отличается от локальной копии:
  git status
  git remote -v
  git fetch origin
  git log --oneline --left-right --graph HEAD...origin/main
  git diff HEAD..origin/main
Сохрани свои незакоммиченные правки commit или осознанным stash. Когда локальных коммитов нет, git pull --ff-only безопасно перемещает ветку вперёд. При расхождении выбери merge либо rebase своих неопубликованных коммитов и реши конфликты. Не начинай с force push.

16. Что обязательно уметь без заученного текста

Открыть Ubuntu и правильную папку; объяснить каждый параметр chmod 744; написать перенаправление/grep/tail; отличить commit от push; создать ветку и убрать конфликтные маркеры; объяснить обе стадии Dockerfile и порты; выполнить CRUD с фактическим id; найти логи контейнера; показать volume после restart; объяснить пять стадий Jenkins и почему тест останавливает pipeline; отличить автоматический запуск от ручного.

Тренируйся в отдельной копии репозитория. Сначала повторяй команды с этой инструкцией, потом без неё и проговаривай смысл. Если дают незнакомое изменение на экзамене, сначала выясни текущий статус, измени один небольшой элемент, проверь локально, затем commit/push и проверь Jenkins.
